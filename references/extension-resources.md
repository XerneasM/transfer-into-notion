# Extension resources and follow-up actions

Read this file only when the source contains consequential resources or dependencies outside the note, or when the user explicitly asks for enrichment or validation. Do not create an extension section merely to fill the template.

## Selection and attribution

Include an item only when it materially helps the user understand, verify, or apply the source's central idea. Preserve its relationship to the primary source:

- 作者明确推荐: the primary author advises using, reading, watching, learning, collecting, or doing it.
- 作者提及但未推荐: it appears as context, an example, or a dependency without endorsement.
- Codex 补充: it is an outside synthesis; explain why it is useful and never attribute it to the author.

Prefer a compact record with 项目｜类型｜与核心内容的关系｜建议动作｜优先级｜来源归属. Merge duplicates and omit decorative or incidental mentions. When multiple embedded or linked authors are present, name the actual source owner instead of collapsing them into the primary author.

## Type-specific treatment

- **Book, paper, course, concept, or theory:** state why it matters and the smallest useful reading or learning target. Give a question to carry into the material instead of producing an indiscriminate reading list.
- **Film, video, podcast, documentary, website, design, artwork, or case:** identify the feature to observe and how it connects to the source's method. Do not turn a passing example into an assignment.
- **Dataset, report, interview, benchmark, or test:** specify what evidence is missing, a plausible source, freshness requirements, and an observable stopping criterion for collection.
- **Technique, method, or prerequisite capability:** define the minimum competency needed, a short practice action, and evidence that the user is ready to continue.
- **App, plugin, Skill, MCP server, library, service, or deployable environment:** use the installation evaluation below only when adoption would materially affect the workflow.
- **Outside action, person, organization, or community:** state the purpose, expected output, and whether the action requires the user's separate authorization.

## Research escalation

Choose the lightest evidence level that supports the decision:

1. **Record only:** the name and role are clear, the fact is durable, and no current decision depends on it. Do not browse.
2. **Light verification:** identity, edition, availability, authorship, data source, or a factual relationship is ambiguous. Verify the smallest set of facts, preferably from a primary source.
3. **Current evaluation:** the item affects installation, deployment, purchase, permissions, privacy, compatibility, pricing, policy, data freshness, or safety. Use current public sources, record 评估日期, and separate official facts, public reports, and Codex inference.

For books, films, videos, podcasts, or courses, verify metadata only when ambiguity or availability matters. For datasets, verify provenance, coverage, update date, and licensing only to the extent needed for the proposed use. For technical questions, prefer primary documentation. Do not treat promotional copy, a single comment, popularity, downloads, or stars as proof of quality.

## Installable-item evaluation

Assess only dimensions that change the user's decision: ease of use, practical benefit, maintenance and compatibility, capability limits, cost, privacy and permissions, license, and reversibility.

When a genuine installation decision is needed, end that item's assessment with one label and a lowest-risk trial path:

- 建议立即安装
- 建议有条件试用
- 暂缓安装
- 不建议安装

Prefer a temporary project or isolated profile, minimal permissions, and a documented rollback. Do not install, deploy, purchase, authorize an account, contact another person, or expose credentials unless the user separately requests that action.

If evidence is insufficient or contradictory, state the uncertainty and choose the more conservative action instead of fabricating confidence.
